# 首字延迟 Profiling · 2026-09-14

## 结果

10 条真实 DeepSeek 官方请求，全部通过原有扫码 Bot 回复到用户飞书会话。4 条基线（2 冷 / 2 热）与 6 条流式优化（3 冷 / 3 热）。原试用模型是 OpenRouter 上的 Claude；本次对照两组均用官方 `deepseek-flash`、关闭 thinking，避免把换模型的收益误算为代码优化。

飞书首字以含真实模型文字的卡片/消息被飞书 API 接受成功计时，不包含客户端渲染和通知延迟，不把占位提示计为首字。测试从调度开始计时，未走真实飞书新消息入站；测试回复走真实飞书 API。生产消息额外记录队列等待时间。

样本量小，仅报告实测范围和中位数，不代表生产 P95/P99。

## 已实施优化

- OpenClaw 原本已经 `stream:true`；原飞书适配器等回复和备份完成才发消息。改为原生 CardKit 流式卡片，收到真实文字就发送，约 800ms 合并后续更新，最终更新同一卡片并关闭流式状态。
- 卡片 ID、消息 ID、更新序号持久化，服务重启和最终回复重试复用同一卡片。流式 API 失败有最终文本回退。
- 热实例复用 SDK 句柄，删除 execute 阶段重复的 Sandbox 获取和超时更新。冷启通过文件版本摘要避免重复部署相同启动脚本。
- 每轮备份改为完整会话状态 + 相对原 payload 的工作文件变更，记录删除清单。此次诊断实测备份 236,256 字节、1.324 秒；文件工具写入、读取以及本地备份恢复测试均通过。主表 10 条样本仍使用旧完整备份，因此整轮完成时间未包含该后续优化收益。
- 修复 SDK 输出已写入 Writable 队列但异步消费者未排空，就提前判定 incomplete 的竞态。现在等待 Writable finish，再判断 response.completed。真实已有会话发现的失败按完整事件及文件证据修复，没有重放工具。

## OpenClaw 冷启动 CPU Profiling

另取一次独立诊断，CPU profile 的启动前约 7.6 秒主要采样如下（采样自耗时，不是可直接相加的完整墙钟解释）：

| 采样热点 | 约耗时 |
|---|---:|
| package_json_reader.get | 1.33s |
| 文件 read | 1.18s |
| 垃圾回收 | 0.97s |
| ESM 编译 compileSourceTextModule | 0.60s |
| internalModuleStat | 0.33s |
| readFileUtf8 | 0.28s |

这表明模块解析/读取和初始化是主要成本。显式 Node 编译缓存没有稳定降低冷启动：基线 OpenClaw 为 6.56–7.22 秒，优化组为 6.06–8.07 秒。不能宣称 OpenClaw 冷启已明显加速。后续值得针对发布包的模块数量、依赖解析和 Gateway 最小入口做专项优化；本轮没有冒险删减原 DealClaw payload 或核心能力。

## 验证与边界

- 10 条性能样本均成功回复；生成期间卡片有多次增量更新。用户随后明确确认“能看到文字逐步出现”，客户端流式显示验收通过。
- 模型 API 直接访问 DeepSeek 官方，thinking 关闭；该选择面向当前聊天首字速度，不代表复杂推理任务的最佳设置。
- 调度服务及数据库仍在 Mac；VM 在 Vercel iad1，网络路径会影响飞书及模型延迟。
- 编译缓存、网络、供应商预填充缓存和上下文长度都会影响结果；不将短提示词无工具样本外推为所有业务任务延迟。

官方参考：[DeepSeek thinking](https://api-docs.deepseek.com/guides/thinking_mode/)、[飞书流式文本](https://open.feishu.cn/document/cardkit-v1/card-element/content)。


## 已有 Bot 最终验收

官方 DeepSeek 在用户原有会话中完成文件工具调用。修复输出排空竞态后，新的一轮只读验收成功，原文 `official-deepseek-stream-914` 被完整返回，任务 succeeded、飞书 delivery=sent；该轮队列等待 138ms、文件工具请求到完整生成约 3.945s、精简备份 1.543s。该轮发生在控制服务重启后，包含启动脚本部署开销，不混入前述热组性能分布。

飞书 IM GET 对 CardKit 2.0 卡片返回“请升级至最新版本客户端，以查看内容”的兼容占位内容，不能用该接口文本回读验证新版卡片内容。卡片创建、增量和最终更新 API 均成功；用户直接确认客户端可以看到文字逐步出现。因此报告区分服务端接收时间与用户确认的视觉效果，不将兼容占位误判为用户客户端故障。
