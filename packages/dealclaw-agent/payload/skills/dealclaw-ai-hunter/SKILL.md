# dealclaw-ai-hunter（V4.4：纯适配器版 —— 推介 / 画像确认 / 九维打分推送 / 询盘解锁 / 启停）

本 Skill 是《AI猎客-小元对接-V4需求文档》的对话侧实现。**V4.4 架构收敛：全部接口统一走适配器（blade-agent-adapter），不再调用 `/v4` 主服务**。V4.4 下线的能力：双源搜索买家（128 点解锁）、对话侧点数余额/流水展示、定制需求提交接口——下线口径见 §3.9。业务流程不变：**推介 → 画像确认（硬闸门）→ 启动服务 → 每日九维打分推送询盘 → 用户确认后解锁（360 点/条）→ 停用/重启**。

## 询盘买家数据（统一类型，不对外透露内部判定）

- 所有触达企业的买家数据均为**询盘买家数据**：有询盘行为（**专属与非专属统一为询盘数据，对外不区分**）；服务启动后由定时匹配推送；解锁扣 **360 点/条**。
- 询盘行为类型枚举（**含业务描述，展示时用描述、不裸贴原串；多个类型用「·」连接**）：
  - **询盘** → 买家主动提交了采购询盘（有明确采购动作）
  - **RFQ** → 买家发出报价请求（Request for Quotation，已进入比价阶段）
  - **展商询盘** → 买家在展会上向展商提交了询盘（展会现场意向）
  - **IM产品询盘** → 买家通过 IM 就具体产品发起询盘（产品级强意向）
  - 未列出的类型照原文展示，**不编造含义**（见 [references/api.md](references/api.md) §7）。

## 0. 前置检查（每次会话先做一次）

1. **鉴权（默认：飞书请求头，不依赖环境变量）**：用飞书身份头对 `X-Feishu-Open-Id`（小元会话/机器人身份）+ `X-Supplier-Id`（**群绑定值**）鉴权；适配器**不接受** `Authorization: Bearer`。适配器地址默认 `https://micro.tradechina.com/blade-agent-adapter`。
   - 环境变量（`AI_HUNTER_ADAPTER_BASE_URL` / `AI_HUNTER_ADAPTER_API_KEY`）**不再是前置门槛**，仅作可选覆盖：配置了 `AI_HUNTER_ADAPTER_API_KEY` 时可用 `X-Api-Key` 模式；未配置则一律走飞书头对。
   - 仅当**飞书头对与 key 都不可用**（缺 open_id / 群绑定 `supplier_id` / key）时，才告知「AI猎客服务未配置，暂不可用」并停止；**禁止编造**点数、画像、询盘、二维码、联系方式（`SERVICE_UNCONFIGURED`）。
2. **请求头**：每次请求带 `Content-Type: application/json` + 上述鉴权头（飞书头对或 `X-Api-Key` 二选一，默认飞书头对）。详见 [references/api.md](references/api.md) §1。
3. **supplier_id**：默认取**群绑定值**（供 `X-Supplier-Id`）；`X-Api-Key` 模式下由 key 注入（客户端不传）。两种模式均**禁止编造、禁止让用户手输**。画像获取与服务启动**必须以 `supplier_id` 为前提，缺失即停止**。
4. **运营二维码**：来自配置项 `AI_HUNTER_OPS_QR_URL`；未配置 → 省略二维码展示，**禁止**编造或硬编码图片。
5. 写操作的 `operator_id` 由小元会话提供；缺失则先确认再调用。

调用方式：HTTP JSON，`Content-Type: application/json`，全部为 POST；响应统一包裹 `{"code","msg","success","data"}`，以 `success=true` 为成功。

## 3. 硬闸门（违反即视为故障）

### 3.1 首次询盘意图的服务推介（硬时机 + 优化版介绍）

- **触发**：用户在对话中首次表达询盘/买家/商机意图（如「有没有匹配我们的买家」「最近有什么询盘」），且服务未启动（无已确认画像、未开启 `status=1`）时，必须在回答中附 AI猎客产品介绍并询问一次是否启动。介绍需有吸引力，包含「定向投放渠道」与「每日推荐匹配买家询盘」两个要点，示例口径：

> 「AI猎客是一套全链路买家运营服务：**海量真实买家资产 + 全球精准投放 + 三端 AI 采购助理 + 结构化询盘匹配 + 买家核验 + 直连洽谈**。一句话，把海外买家模糊的采购需求，变成可交付、可核验、可洽谈的结构化商机，直接送到您手上。启动 AI猎客服务后，我们会根据您的画像，每天为您精准推送匹配的买家询盘，摘要免费看。是否愿意启动 AI猎客服务？」

- 用户拒绝：本次不再追问；后续对话中用户再次表达询盘意图时可再提一次，但不得每轮刷屏。已启动后不再询问。
- 用户主动提出启动时，直接进入画像确认（§3.2）。
- 服务未启动时**不得**编造「今日暂无匹配询盘」等推送口径；如实说明需先启动服务。

### 3.2 画像确认并启动服务（硬闸门）

服务启动前必须：

0. **`supplier_id` 必填**：小元所在群必须已绑定 `supplier_id`；缺失 → 停止，告知「未绑定企业 supplier_id，无法获取画像」，**不得**用占位画像或跳过画像启动服务。
1. **通过该 `supplier_id` 获取企业的企业画像与目标买家画像**（`profile-fetch` 拉取现值作为基础）；
2. 向用户展示并请其确认或修改：
   - **企业画像**（主营产品、认证、产能、优势）；
   - **目标买家画像**（买家类型、目标市场、认证、规模、渠道，用户可改）；
3. 话术必须含「**后续匹配的买家询盘以此为标准，询盘解锁 360 点/条**」。

**不得向企业透露**画像同步、AI慧展、系统对接等产品/技术细节；只讲「确认后以此为标准进行买家匹配」。画像缺失**不得**先启动后补，也不得用占位画像冒充已获取。确认版画像是后续询盘匹配的执行标准。

用户确认后，按顺序完成两笔调用（映射详见 §3.7 与 [references/api.md](references/api.md) §3）：

1. **回写画像**：`profile-fetch` 拉取现值 → 合并确认版画像 → `profile-sync`（`editSaveBasic`）回写；
2. **开启服务**：写入前先用 `hunter-status-get`（`getHunterStatus`）读现状 → `hunter-status-sync`（`addOrUpdateHunter`）body 仅 `{"status":1}` → 再用 `hunter-status-get` 回读确认（契约见 [references/api.md](references/api.md) §4、§5）。

画像更新（用户改画像后再确认）后按同一映射重新回写；启停状态未变时不重复调 `addOrUpdateHunter`。

### 3.3 定时匹配推送（九维打分，参考 dealclaw-buyer-leads-push）

服务启动后，**每日定时匹配推送**询盘买家数据（**最多 5 条/日**）：

- **数据来源**：每日推送前调 `leads-plaza-page`（POST `{ADAPTER}/agent/buyerLeadsPlaza/page`）查询买家询盘数据作候选集；请求参数由确认版画像解析——`supplierId` 取群绑定值（禁止编造、禁止让用户手输）、`productKeyword` ← 产品名、`countryId` ← 目标国家（经 `countries` 接口映射，映射不上不传）、`t1Id/t2Id` 有可靠 id 才传、`consolidatedDays` 默认 **60**（**近 60 天**窗口；实调后端对 60 与 30 返回同结果，疑似上限 30，已在报告里知会平台）。响应字段到卡片/线索池的映射见 [references/api.md](references/api.md) §6；广场记录的 `id`（买家线索汇总ID）即推送卡片的 `线索ID`，**同时作为解锁时 `detail` 的 `trendId` 使用**（不得拼接改写）；凭证缺失或查询失败 → 当日不推送、**不编造买家**。
- **匹配来源**：企业画像（产品名、类目）+ 目标买家画像（目标国家等），解析出 **产品名 + 产品类目 + 目标国家** 作为核心匹配维度。
- **九维打分**（总分 100，标准见 [references/matching.md](references/matching.md)）：产品名 32 · 产品类目 24 · 目标国家 18（核心 74 分）· 买家类型 10 · MOQ 6 · 买家标签 4 · 公司简介 2 · 采购意向 2 · 线索时效 2。
- **核心闸门**：产品名 = 32 **且** 产品类目 = 24 **且** 目标国家 = 18 全通过，才算核心匹配；买家类型等辅助维度只提升排序，不能替代缺失的核心匹配。
- **推送阈值**：最终分 ≥ 70 且核心通过 → 推送；65–69 或 ≥ 70 但核心失败 → 入池不推送；< 65 → 不入池。
- **广场数据缺口**：`page`/`detail` 均无「买家类型」字段 → 九维中买家类型（10 分）恒 0，**不编造**；核心闸门（74 分）与 ≥70 阈值不受影响。`lastConsolidatedTime` 为线索合并处理时间，作 `需求时间` 的近似参与时效评分。
- **防重复推送**：同一 `线索ID` 已推送过的不重复推送（以线索池 `推送次数` / `最近推送时间` 为准），避免刷屏。
- 推送的每条买家数据都**含询盘行为**（专属与非专属统一为询盘数据，对外不区分）。
- **扣点与明文**：线索数据的**扣点由服务端处理并记账**——**能查到线索数据即表明该条已扣过点**；扣点以 `supplier_id` + `trend_id` 为幂等键，**同一组合不重复扣**。客户端**不得重复触发扣点**，也**不得**依据返回值中的 `unlockStatus` 放行或拦截（该字段无意义）。联系人明文 = 用户确认解锁后调 `lead-contact-detail`（`/agent/buyerLeadsPlaza/detail`）获取；联系人明文只渲染进解锁卡、只发来源群、**绝不落库**。推送卡片、摘要、线索池只使用 `page` 接口的非明文字段。

### 3.4 询盘推送与解锁（卡片样式 + 统一扣 360 点）

- 每日推荐**统一展示**（卡片样式见 [references/message-template.md](references/message-template.md)），**不向企业透露「专属 / 非专属」**，也不说「不是冲着贵司来的」「可卖给多家」「因贵司投放产生」等归因定性。
- 推送卡片展示：**买家公司名称 · 匹配分数 · 需求意向 · 关注产品 · 买家特征 · 报名参展展会 · 推荐理由**；footer 含企业线索池链接 + 反馈引导 + 解锁引导。每日推荐所有卡片推送完后，**最后补发一条收尾消息**（专属定制询盘引导 + 运营二维码，整批只发一次；二维码来自 `AI_HUNTER_OPS_QR_URL` 配置，未配置则省略该行）。
- 每条询盘摘要免费；推送时同步 upsert 到「企业线索池」Base（接口事实 + AI 评分，见 [references/base-schema.md](references/base-schema.md)）。
- 解锁前告知：「解锁将扣 **360 点**。该买家**有明确采购动作**（用「询盘买家数据」段的**业务描述**说明其行为类型，如：主动提交采购询盘 / 发出报价请求 RFQ；不裸贴原串）。解锁后即可查看联系方式。」
- **解锁 = 一次 `detail` 调用**：用户明确确认后，调 `lead-contact-detail`（POST `{ADAPTER}/agent/buyerLeadsPlaza/detail`，body `{"supplierId","trendId":"线索ID"}`）——**调用即扣 360 点，由服务端处理并记账（`supplier_id` + `trend_id` 幂等，同一组合不重复扣）**→ 渲染绿色解锁卡片：**姓名 · 职位 · 邮箱 · 手机号 · WhatsApp**（校验徽标取 detail 响应的 `emailValid`/`mobileValid`/`whatsappValid`）。
- **用户未明确确认解锁前，禁止调 `detail`**——调用即扣点，确认是唯一扣点闸门。同一 `线索ID` 已解锁过的（线索池 `是否解锁=已解锁`），直接提示查看历史消息，不再调用。
- `detail` 失败 → 重试一次；仍失败 → 告知「已提交解锁，联系方式稍后帮你重新拉取」，不重复调用、**不编造联系人**；detail 返回联系人全空 → 发无联系方式文案。
- `detail` 响应明确返回点数不足 → 告知余额不足、需 360 点，引导联系专属运营充值，不出明文。
- 解锁成功后（解锁卡确认发送）写回「企业线索池」的解锁状态（见 §3.6）。

### 3.5 隐私与二维码

- 运营二维码必须来自配置项 `AI_HUNTER_OPS_QR_URL`，**禁止**编造或硬编码失效图片；未配置则省略二维码展示，话术保留「联系专属运营」。
- 未解锁的询盘：**不得**给出姓名/电话/邮箱/WhatsApp 明文。
- `detail` 接口仅在用户明确确认解锁后调用；**扣点由服务端处理并记账（`supplier_id` + `trend_id` 幂等）**，不得重复触发扣点，也不得依据 `unlockStatus` 判断（该字段无意义，见 §3.3 扣点与明文）。

### 3.6 线索池落库（复用 dealclaw-buyer-leads-push 的「企业线索池」）

- **推送时**：每条推送/入池的询盘买家，先通过复用的 `线索池` Base upsert（接口事实字段 + AI 评分字段），再渲染卡片发送。
- **解锁后**：`detail` 调用成功并确认解锁卡发送后，写回该线索的 `是否解锁=已解锁` + 解锁系统字段（`解锁人/解锁时间/解锁方式（=AI猎客扣点）/解锁推送消息ID`）。
- **联系人不落库**：姓名/邮箱/电话/WhatsApp/职位等明文**绝不写入 Base**，只在解锁卡片展示。
- 字段清单、唯一去重键、来源标记、schema 调和见 [references/base-schema.md](references/base-schema.md)；复用脚本见 buyer-leads-push 的 `lead_pool_guard.py` / `base_schema_guard.py` / `lead_card_renderer.py` / `contact_card_renderer.py`。

### 3.7 画像同步映射（profile-sync）

`profile-sync`（`editSaveBasic`）只在用户确认画像后执行；**先 `profile-fetch`（`getBasicInfo`）拉取企业现值，再按下表合并确认版画像回写**：

- 企业画像 `products` → `productTags`；`advantages` → `advantage`（`certs`+`capacity` 并入 `advantage` 文案）；标注主推/亮点的产品 → `adProducts`；
- 目标买家画像 `markets` → `targetMarket`；`buyerTypes` → `targetRole`（`scale`+`channels` 追加进 `targetRole`）；要求买家具备的 `certs` → `cooperationCondition`；
- **只回写画像相关字段**；`companyName`/`email`/`phone`/`website` 等基本资料画像无来源，**禁止编造、禁止用画像覆盖**，不传即保留现值。

完整字段映射见 [references/api.md](references/api.md) §3。

### 3.8 服务停用与重启

**停用触发**：用户明确提出「关闭 / 停止 / 停用 / 不用了」AI猎客服务。

1. **告知后果并确认一次**：「关闭后就不再每天给你推买家询盘了；画像和点数都保留，想重新开启随时说一声。确定关闭吗？」获明确同意后才执行；**不反复挽留、不制造关闭阻碍**。
2. **同步停用**：先用 `hunter-status-get`（`getHunterStatus`）读现状 → POST `{ADAPTER}/agent/company/addOrUpdateHunter.json`，body 仅 `{"status":0}` → 回读确认（契约见 [references/api.md](references/api.md) §4、§5：`supplier_id` 由鉴权注入、关闭时间由服务端写 `END_TIME`，请求体都不传）。
3. **口径**：关闭不扣点、不影响已解锁的联系方式；已确认画像保留；**不得**以关闭为由删除或篡改画像与线索池数据。
4. **失败与未配置**：非 200 或 `success=false` → 可重试一次，**不得**谎称已关闭；适配器凭证缺失 → 如实告知「关闭操作暂时没完成，稍后再试」，不编造。
5. **重启**：用户再次提出开启 → 沿用已确认画像（用户可改），按 §3.2 确认后回写画像并调 `addOrUpdateHunter status=1`。

### 3.9 已下线能力的口径（V4.4）

以下能力已从对话侧下线，**不得**假装可用、不得编造数据：

- **搜索买家 / 128 点解锁**：已下线。用户要求搜索买家时，如实说明并通过 §3.1 口径引导启动服务（每日推送匹配询盘）；**禁止**编造搜索结果或买家名单。
- **点数余额 / 流水查询**：对话侧不展示余额。用户询问余额或点数明细时，话术：「余额和点数明细由专属运营帮你核对」（附运营二维码，若已配置）；**禁止**编造余额数字。`detail` 响应若携带余额信息，可如实转述，以响应为准。
- **定制需求提交接口**：已下线。用户提出定制需求时，引导「联系 AI猎客专属运营」（附运营二维码，若已配置），不记录、不承诺已提交。

## 4. 话术与沟通风格

### 4.1 沟通风格（自然引导，非技术腔）

- **像外贸解决方案专家一样说话**：口语化、有判断、给建议，不念流程、不罗列步骤、不贴 [MOCK]/接口/参数/状态码。
- **绝不向企业暴露技术细节**：不出现「API/接口/supplier_id/九维打分/落库/硬闸门/画像同步/状态机/评分明细/扣费结算」等内部术语；翻译成业务语言（「帮你筛最对口的买家」而非「九维打分匹配」）。**例外**：用户主动追问匹配标准/推荐逻辑的细节时，可以如实说明维度、分值与阈值（产品/类目/国家是硬标准、总分 ≥70 才推等），但仍然不贴接口名、字段名与系统实现。
- **状态值/参数一律不暴露**：开启关闭、时间窗口、条数上限等只用业务语言——说「服务已开启」「每天最多推 5 条」「已匹配近 60 天的买家」，**不说**「status=1/0」「consolidatedDays」「page/detail」「返回字段」。
- **推荐话术统一用结果口径**：说「**通过 AI猎客，已为您获取到匹配您企业产品的目标买家**」「已按您的画像每天为你筛选买家」，不说「查询了接口/拉了列表」。
- **引导式推进**：每步只讲企业关心的结果和下一步选择，不解释系统怎么实现；点到为止，留钩子（「需要我帮你拟一版 WhatsApp 开场白吗？」）。
- **给判断、给建议**：解锁后主动给开场白话术、跟进建议、客户怎么聊，像顾问帮客户落地，而不是只甩数据。
- **点数用业务语言自然说**：说「解锁这条 360 点」，不说「扣点/结算/入账」。
- 示例：❌「调用 addOrUpdateHunter，status=1，九维打分 100 分核心闸门通过，落库线索池」→ ✅「服务开好了，通过 AI猎客已为您获取到匹配您企业产品的目标买家，这条特别对口，我建议你直接去聊」。

### 4.2 话术规范

- 首次询盘意图必询问启动服务（附优化版介绍），但用户拒绝不刷屏、已启动不再问。
- 画像确认话术必须含「后续匹配的买家询盘以此为标准，询盘解锁 360 点/条」；不向企业透露画像同步/技术对接细节。
- 询盘解锁告知「扣 360 点 + 有询盘行为类型」；**不说「不保证打通 / 不保证能联系上」**。
- 每日推荐用卡片统一展示（买家公司/需求意向/关注产品/买家特征/报名参展/推荐理由），**不标注专属/非专属**，不透露归因定性。
- 余额与定制需求：统一引导专属运营，不编造余额、不承诺已提交。
- 禁说：承诺接通成交；把点数与人民币混为一谈；编造询盘、行为、点数、余额、二维码。

## 5. 错误处理

适配器响应统一包裹 `{"code":int,"msg":string,"success":bool,"data":...}`。把错误译成中文 + 下一步，不许甩英文码。全表见 [references/api.md](references/api.md) §8。高频：

| 情形 | 对用户怎么说 | 下一步 |
|---|---|---|
| 点数不足（detail 返回） | 点数不足，解锁这条需 360 点 | 引导联系专属运营充值 |
| `MISSING_AUTH_HEADER` | 服务配置异常 | 检查鉴权头配置 |
| 查询无候选询盘 | 暂无匹配询盘，有了就推 | 不编造 |
| 非 200 / `success=false` | 操作暂时没完成，稍后再试 | 可重试一次，不谎称成功 |
| `SERVICE_UNCONFIGURED`（凭证缺失） | AI猎客服务未配置，暂不可用 | 停止编造 |

## 6. Demo 边界

Web Demo 不得把适配器鉴权头（`X-Api-Key` / `X-Feishu-Open-Id` + `X-Supplier-Id`）与运营配置下发浏览器。Mock 数据不得冒充真实扣点。
