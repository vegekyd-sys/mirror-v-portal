# Chat-isolated resource access

Apply this policy to every generated draft Docx, formal Docx, and buyer-lead Base. `chat_id` is the only group identity. Never enumerate members and never grant access from a company-name or title search.

## Required sequence

1. Require one invocation `chat_id` and one state record for that exact ID.
2. Create the resource privately and capture its token plus actual owner, creator principal, credential type, and roles. Every resource generated by this Skill must be created with an authorized current-group user's `user_access_token`; the creation response token and that same user token must flow directly into `scripts/feishu_permission_fix.py authorize-created`. Do not publish between creation and authorization. For a separately supplied existing resource, read its owner/collaborator state by explicit token and use the existing-resource handoff path.
3. Run `scripts/permission_handoff_guard.py plan`. Follow only its result: DealClaw may authorize directly when owner/full-access; otherwise the creator/owner must hand off; an invisible app must first join the target group; an unpublished unmanageable resource must remain private and be recreated; an existing unmanageable resource requires owner action.
4. **Permission-actor membership preflight.** Resolve the authenticated actor from the credential, never from caller input: user token through `GET /open-apis/authen/v1/user_info`, tenant token through `GET /open-apis/bot/v3/info`. Verify membership with `GET /open-apis/im/v1/chats/{chat_id}/members/is_in_chat` and require `data.is_in_chat=true`. For `authorize-created`, additionally require that the user-token actor is the live resource owner before any permission write. If any check fails, stop; this Skill does not silently invite an actor into a group.
5. **Response-code verification.** Check the response code of every permission API call (public-permission update, member add/update/delete/list). Any non-zero code or HTTP error is terminal: keep the resource private, surface the code and message, and never continue to posting, binding, or activation. An unchecked failed grant must never be treated as success.
6. Using only the selected verified owner/full-access actor, update public permissions:

```json
{
  "external_access_entity": "closed",
  "link_share_entity": "closed",
  "manage_collaborator_entity": "collaborator_full_access",
  "security_entity": "only_full_access"
}
```

7. Add/update the configured DealClaw application OpenID as `full_access` unless it is the owner. Then add/update exactly one group collaborator:

```json
{
  "member_type": "openchat",
  "member_id": "<binding.chat_id>",
  "perm": "edit",
  "perm_type": "container",
  "type": "chat"
}
```

Use add-or-update semantics: if the collaborator already exists (the add call reports a duplicate), update its permission to `edit` instead of failing. Use resource type `docx` for documents and `bitable` for Base, pass `need_notification=false` on member writes, and set the query `type` to the resource type on every permission call. With `tenant_access_token`, require the calling application to be installed as a bot in the target group before granting `openchat` (see the preflight in step 4). The creator app and DealClaw app may differ; the creator must grant DealClaw management before credential switching.

8. Remove unexpected explicit collaborators, retaining only owner, permission actor, DealClaw full-access principal, configured administrators, and the exact group.
9. Re-read public permissions, owner, actor role, and collaborators. Normalize `resource_owner`, `permission_actor`, `automation_principal`, timestamps, observation ID, and context for `resource_permission_guard.py`. `chat-isolation-v3` must prove exactly one group `edit`, DealClaw `owner/full_access`, and actor collaborator-management authority. Snapshot age is at most 60 seconds. `scripts/feishu_permission_fix.py snapshot` emits a compatible snapshot directly from live data.
10. Persist only the validated redacted proof. On any failure, keep the resource private and do not post, bind, activate, query, write, or push.

**Publish order.** A message containing the document or Base URL must never be sent before step 10 succeeds. The order is always grant → live readback → persist proof → post link. Sending the link first is the direct cause of group members hitting an access-denied page.

Use Drive v2 permission-public APIs (`GET/PATCH /open-apis/drive/v2/permissions/{token}/public`, response under `data.permission_public`) and verified Drive permission-members APIs for `type=docx` or `type=bitable`. The caller must itself have permission to add collaborators. Do not use the deprecated/wrong v1 public-permission route, do not flatten the v2 response incorrectly, and do not interpret HTTP 403 as permission to switch to public sharing.

## Proof placement

- Store a draft proof as `onboarding.draft_permission_proof` before posting the review link.
- Store active formal proofs under `resource_permissions.formal_document` and `resource_permissions.base`.
- Require `resource_permissions.permission_chat_id == state.chat_id == binding.chat_id`.
- Require proof token fingerprints to equal the fingerprints of the stored formal Docx and Base tokens.
- Use a binding/draft operation ID as context while creating resources. Immediately before write/send, obtain two new, distinct readbacks with `verification_context_id = run_context_id`; a persisted binding proof is not a live delivery proof.

## Existing and inherited access

Closing link sharing does not remove existing explicit collaborators or inherited access. Clean existing collaborators before validation. Create resources in a private, non-shared location; if a resource is inside a shared folder or Wiki space, also prove that parent/space membership cannot grant access to a person outside the bound group. Otherwise fail closed.

The owner, verified permission actor, DealClaw automation identity, and enterprise administrators may retain management rights. Do not describe them as ordinary group-only access.

## Existing resources created by another app

If “AI猎客” or another app created the Base and DealClaw lacks owner/full-access, DealClaw cannot repair it alone. Use the creator app credential or owner user's `user_access_token` to grant the exact `openchat/chat_id` `edit` and DealClaw application OpenID `full_access`, while keeping link sharing closed; then validate `chat-isolation-v3`.

If that credential is unavailable, return `EXISTING_RESOURCE_OWNER_ACTION_REQUIRED`. Ask the owner to invite the current group as editable collaborator and the configured DealClaw application identity as full-access collaborator, while keeping external/link sharing closed. Re-read and validate before proceeding. Never ask for public or tenant-wide editing.

## External group members

This policy version is for internal-only groups and requires `external_access_entity = closed`. If the bound group contains external-tenant members who must edit, stop with `EXTERNAL_GROUP_MEMBER_POLICY_REQUIRED`; do not silently open external access. A separately approved policy version must keep link sharing closed and still grant only the exact `openchat` group.

## Standard flow: owner-user creation (mandatory for generated resources)

The authorized current-group user creates the resource with their own `user_access_token`. Creation, authorization, proof persistence, and publication are one fail-closed unpublished operation:

1. Create the Docx/Base as the user and retain the same user token only for this operation.
2. Run `feishu_permission_fix.py authorize-created` with the exact returned resource token. It resolves the user OpenID, proves that user is in the target group, and proves the same user is the live resource owner before writing permissions.
3. Close public permissions through Drive v2 (`external_access_entity=closed`, `link_share_entity=closed`, `manage_collaborator_entity=collaborator_full_access`, `security_entity=only_full_access`).
4. Grant the group as one collaborator: `member_type=openchat`, `member_id=<binding.chat_id>`, `perm=edit`, `perm_type=container`, `type=chat`. Never grant individual members instead — the `openchat` grant automatically covers group joiners and leavers, and individual grants fail `chat-isolation-v3`.
5. Grant the DealClaw application OpenID `full_access` (`member_type=openid`, `perm_type=container`, `type=user`) so the scheduled run can read the knowledge document and write the Base without further asks.
6. Prune unexpected explicit collaborators, perform a live readback, validate `resource_permission_guard.py` under `chat-isolation-v3`, and persist only its redacted proof.
7. Post the URL only when `authorize-created` returns `status=verified` and `publish_allowed=true`.

The user token must carry the Drive permission-management scopes; a scope failure surfaces as a non-zero response code and is terminal. Use this same flow for the draft Docx, the formal Docx, and the Base. `authorize-created` is not a generic repair command: it accepts only the live owner's user token. Use `repair --user-token` for an existing resource only after explicit owner/full-access validation, then produce a fresh snapshot and validate it before reposting.

## Diagnosing and repairing access failures

When group members report they cannot open a bound or newly posted resource, do not guess. Run `scripts/feishu_permission_fix.py diagnose` against the exact stored token and `chat_id`; it reports which failure is present:

- `PERMISSION_ACTOR_NOT_IN_CHAT` — the authenticated user/app is not in the group, so the `openchat` grant cannot be trusted. Have an authorized group administrator add the actor, then rerun; the Skill never auto-invites it.
- `MISSING_GROUP_GRANT` — no `openchat` collaborator exists for the bound chat (the grant failed silently or was made to individual users). Rerun `repair`.
- `GROUP_GRANT_NOT_EDIT` — the group grant exists with the wrong permission. Rerun `repair` (add-or-update fixes it in place).
- `CANNOT_READ_RESOURCE` / `DEALCLAW_NOT_COLLABORATOR` — ownership handoff is broken; use the creator credential or follow the existing-resource owner-action path.
- `PUBLIC_SETTING_DRIFT` — public/link settings were reopened; `repair` closes them again.

Then run `scripts/feishu_permission_fix.py repair` (use `--dry-run` first), and finish with `scripts/feishu_permission_fix.py snapshot` piped to `resource_permission_guard.py validate` to produce the `chat-isolation-v3` proof before reposting any link.
