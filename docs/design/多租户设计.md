# 详细设计：每租户专用 dealclaw-agent Pod（不拆分 k8s namespace）

> 状态：Draft  
> 日期：2026-08-02  
> 适用环境：dealclaw-staging / dealclaw-prod  
> 关联模块：Provisioning Service、Nexus Agent Gateway、DealClaw Agent、Central Gateway(Onboarding)

## 1. 背景与问题

当前多租户方向需要同时满足：
- 租户隔离：一个租户一个专用 Agent（至少进程/Pod 级别隔离）
- 运维可控：避免为每个租户创建独立 k8s namespace 导致 namespace 数量膨胀、RBAC/监控/巡检复杂度上升

本设计决定：
- 保留“每租户一个专用 dealclaw-agent Pod”的隔离语义
- 不再默认“每租户一个 k8s namespace”

## 2. 设计决策

### 2.1 决策
- 每个租户创建一个专用 `dealclaw-agent` 工作负载（Deployment+Service，1 副本起）
- 所有租户工作负载都运行在对应环境的共享 namespace 内：
  - Staging：`dealclaw-staging`
  - Production：`dealclaw-prod`
- 不创建 per-tenant namespace

### 2.2 非目标
- 本设计不要求每租户独立 `nexus-gateway`（gateway 继续共享部署）
- 本设计不引入多集群/跨地域隔离
- 本设计不讨论企业版“更强隔离”（未来可扩展）

## 3. 总体架构

### 3.1 逻辑视图（简化）
- Ingress/回调入口（飞书 webhook/WS） → 共享 Gateway（按 tenantId 路由） → 租户专用 dealclaw-agent

### 3.2 关键路由约定
- 每个租户一个 Service：
  - `dealclaw-agent-<tenantId>`
- gateway 转发目标（同 namespace）：
  - `http://dealclaw-agent-<tenantId>:18789/execute`

## 4. K8s 资源模型

### 4.1 命名规范
- Deployment：`dealclaw-agent-<tenantId>`
- Service：`dealclaw-agent-<tenantId>`
- Secret：`dealclaw-agent-<tenantId>-secrets`（或按功能拆分，如 bot/keys/credits）

### 4.2 Label 规范（建议）
- `dealclaw.io/tenant-id: <tenantId>`
- `dealclaw.io/component: dealclaw-agent`
- `dealclaw.io/plan-tier: starter|pro|enterprise`
- `app: dealclaw-agent`

用于：
- NetworkPolicy 按 label 做租户隔离
- 监控/日志按租户维度聚合
- Ops Agent 做巡检、重启与清理

### 4.3 资源与副本建议
- 默认每租户 1 副本
- 高价值租户可提升副本数或资源限额（由 Ops Agent/后台运维触发）

## 5. Provisioning Service 改造要点（契约层）

### 5.1 输出字段
在 Tenant Registry 中新增/补充：
- `runtime_namespace`：`dealclaw-staging` / `dealclaw-prod`
- `agent_service`：`dealclaw-agent-<tenantId>`

Provisioning 在创建租户后返回：
- `runtimeNamespace`
- `agentService`

### 5.2 K8s 操作清单（目标）
- 创建 Secret（租户 bot/keys 等）
- 创建 Deployment（dealclaw-agent-<tenantId>）
- 创建 Service（dealclaw-agent-<tenantId>）
- （可选）创建 NetworkPolicy（按 tenant label 限制流量）

不再创建：
- Namespace（per-tenant）

## 6. Tenant Registry / 数据库设计

### 6.1 tenants 表（概念字段）
- `runtime_namespace`：环境 namespace（不唯一）
- `agent_service`：租户 agent service（唯一，用于路由）

说明：
- `tenant_id` 仍是业务租户的唯一标识
- `agent_service` 是运行时路由锚点（避免 gateway 里到处拼接规则）

## 7. 消息链路（关键路径）

### 7.1 Webhook/WS → Agent
- gateway 收到事件后解析出 `tenantId`
- 通过 `agent_service` 定位到目标 Service
- 转发到 `POST http://dealclaw-agent-<tenantId>:18789/execute`
- Agent 返回统一结构化响应（`result.summary` 为主要输出）
- gateway 将 summary 回发到 IM 平台

### 7.2 可观测性要求（最小集）
- traceId（tenantId + messageId + timestamp）
- agent_url
- agent_status + agent_ms
- feishu_reply_status + total_ms
- error.cause/stack（用于 DNS/连接拒绝/超时排查）

## 8. 安全与隔离

### 8.1 秘钥隔离
- 每租户 Secret 独立，挂载到对应租户 agent Pod
- 禁止跨租户读取（RBAC + 命名规范 + 运维流程控制）

### 8.2 资源隔离
- 同 namespace 下通过 LimitRange/ResourceQuota 做全局保护
- 每个 tenant 的 Deployment 设置 requests/limits
- 可选：按 tenant label 做 NetworkPolicy

## 9. 迁移计划（从现状到目标）

1) 文档对齐（本次）
2) Provisioning：实现 per-tenant Deployment/Service 创建逻辑（同环境 namespace）
3) DB：补齐 `agent_service/runtime_namespace`（迁移与回填策略）
4) Gateway：按 tenant 路由到 `dealclaw-agent-<tenantId>`（不再依赖 per-tenant namespace）
5) 测试：更新 kind 集成测试断言（Deployment/Service 存在）
6) 灰度：只灰度单租户 agent（deployment/dealclaw-agent-<tenantId>）

## 10. 风险与应对

- Service/Deployment 数量增长：通过命名、label、清理机制与 Ops Agent 巡检可控
- 共享 namespace 故障域更大：用 requests/limits + Quota + NetworkPolicy 降低相互影响
- 配置漂移：以 tenant registry 的 agent_service 为唯一“路由锚点”，避免硬编码
