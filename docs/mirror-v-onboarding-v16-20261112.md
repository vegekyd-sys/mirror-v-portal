# Mirror V 上手引导 v16 · 发布与自测记录

日期：2026-11-12（Asia/Shanghai）
版本：payload `mirror-v-full.v16.4`；Portal release `6af40e94`（控制面与 payload 同一提交）
范围：只影响**新扫码**的 mirror-v-full 租户。老租户停在开号时的 payload，不随本次升级。

## 为什么改

10 月中以来 4 个 mirror-v-full 测试号的对话全部发生在开号第一天，之后没有人回来；而记忆要在之后几晚的整理里才长出来。v15 的引导有三个问题：

1. 开场是五选一菜单，主人没看到任何好处就被要求做选择。
2. 飞书这条路太长：准备工具 → 去开放平台开权限、发版本 → 设备码授权 → 盘点 → 选空间 → 读，来回五六轮。
3. 进度全靠模型自己写回：0.3 把 87 份文档读进来后，进度仍停在「选来源」。

## 现在的流程（先做后问）

| 步骤 | 主人做什么 | 平台 / Agent 做什么 |
|---|---|---|
| 扫码 | 扫码 | 建应用时就申请读文档的用户身份权限（`feishu-register.ts` 的 `registrationScopes`） |
| 开场 | — | 一条消息：开场白 + 授权链接与二维码（`feishu-docs.py connect`，快照预装 lark-cli） |
| 授权 | 点链接，回「好了」 | `connect --finish` → `read`（盘点 + 读，限时约 3 分钟） |
| 初稿 | — | 读得快（`draftNow`）就当场写「我对你的理解」，否则排一次性任务写，写完直接发给主人 |
| 纠正 | 指出哪里不对 / 回「对」 | 改记忆页（标「主人确认」），提交；平台把后台发出的初稿附在主人回复前 |
| 补充 | 可选：官网 / 别的 AI 的记忆 / 粘贴 | 同 v15 |
| 收尾 | 起名 | 报账、写 IDENTITY / USER、`onboarding:` 提交，进度 done |
| 之后每晚 | 可能回答一个问题 | Librarian 汇报第二行说一件学到的具体事实；碰到只有主人能定的矛盾，`librarian-ask.py` 问一个问题，平台在主人回答时把问题附上 |

进度由 `onboard-progress.py get` 先按事实校正（有 `onboarding:` 提交 → done；有初稿 → draft；读进了飞书文档 → reading），只往前不往回。

## 自测（Claude 在合成租户上，无飞书长连接）

合成租户 `mvfull-onb-01…05`：不设 `app_id`（不开飞书长连接），lark-cli 绑定 0.3 的应用（已开读文档权限），设备码授权由 Tianyi 的浏览器会话确认（同一应用、此前已授予的同一组权限）。消息走 Portal `/api/messages`，结果读 `elastic_runs`。

| 场景 | 结果 |
|---|---|
| 扫码开场（v16.4 快照） | 16 秒送达一条消息：开场白 + 授权链接 + 二维码；进度 `feishu_auth` |
| 授权后「好了」 | 授权确认 → 读 69～74 份 → 当场写初稿（5～6 分钟，单轮上限 10 分钟）；`memory: 上手初稿` 提交，进度 `draft` |
| 初稿由后台任务写 | 一次性任务 28 秒写完并作为新消息发出；主人在没见过初稿的会话里纠正，Agent 准确改了三页 |
| 纠正初稿 | 改 USER 与项目页、标「主人确认」、保留旧事实，`memory: 主人更正初稿` 提交，进入补充步骤 |
| 补充 AI 记忆 → 起名 | 报账（88 份、约 17 万字、约 7 晚）、数据位置说明、起名「小镜」，`onboarding: 小镜` 提交，进度 done |
| 主人先开口派活、无飞书 | 先完成派的活，再接开场；接不上飞书时不让主人另建应用，转去要官网；读 versa-ai.com 后给出初稿 |
| 夜间 Librarian | 汇报第一行进度、第二行一件具体事实；可达性 4/4，提交通过 |
| Librarian 提问 → 主人回答 | 新会话里平台附上问题；Agent 改两页、旧说法挪进 history、标为已回答 |

自测中发现并修掉的问题：

- 平台发起的开场这一轮没有可回复的消息，只发最终输出，工具前说的开场白会丢（主人只会收到一个链接）→ 引导把开场白写进最终回复；平台对这类轮次也把工具前的话放在答案前（`FeishuEdge.withNarration`）。
- 个人文档库要 `wiki:wiki:readonly`，缺了整库读不到 → 扫码时申请；授权时一并申请应用已开的可选权限。
- manifest 收进了本地 `__pycache__`，快照构建失败 → `gen-manifest.mjs` 跳过。
- 当场写初稿还是排后台任务交给模型判断时间不可靠（一轮 354 秒）→ `read` 输出 `draftNow`。

## 没能自测的部分

- **扫码建应用时飞书是否真的开通了声明的用户权限**：二维码里确认带上了 6 项权限（解码 `addons` 核对过），但飞书创建页在创建前不列权限，只有真扫码创建一次才能确认。若飞书没认，`connect` 会返回 `grant`，退回 v15 的「开通权限链接」路径，不会卡住。
- 真实飞书里的卡片呈现（开场一条消息、二维码图片、流式卡片里的进度）：合成租户不经飞书，靠单测与事件核对。

## 回滚

`/opt/nexus/previous` 指向上一个 release；`deploy-mirror-v.sh activate <上一个 release>` 即可切回控制面。payload 回滚需用上一版 payload 重建快照（`config.json.before-mirror-v-full-*` 备份里有之前的快照 ID）。
